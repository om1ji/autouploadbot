# autouploadbot

Бессерверный бот следит за каналами YouTube и выкладывает каждое новое видео
в Telegram как MP3 с обложкой, исполнителем и названием. В подписи — ссылка
«Original upload» на исходное видео.

Бот целиком живёт в AWS Lambda и стоит центы в месяц: платить приходится
только за хранение образа в ECR и немного чтений DynamoDB.

## Как это работает

Новые видео приходят **двумя независимыми путями**, и оба ведут в одну
очередь SQS:

| Путь | Что запускает | Задержка | От чего зависит |
| --- | --- | --- | --- |
| **Push** | хаб WebSub присылает в `WebhookFunction` подписанную запись Atom | секунды | от подтверждённой подписки на хабе |
| **Poll** | `PollFunction` раз в 15 минут читает RSS-фид каждого канала | до 15 мин | только от YouTube |

Оба пути дают одинаковые сообщения, в которых указан канал YouTube.
`ChannelsTable` в DynamoDB сопоставляет каждому каналу YouTube один или
несколько чатов Telegram. Так у канала может быть своё зеркало, несколько
каналов могут писать в один чат, а один канал — в несколько. Таблицу правят
кнопками из [служебного чата](#служебный-чат), а функции читают её при каждом
запуске, поэтому для нового канала или зеркала деплой не нужен.

Перед отправкой в каждый чат воркер занимает в DynamoDB ключ `videoId#chat`.
Поэтому каждый чат получает видео ровно один раз — даже если оно пришло обоими
путями, если YouTube повторил уведомление после правки названия или если SQS
доставил сообщение дважды. Если не удалась отправка в один чат, повтор уйдёт
только в него. Звук скачивается один раз, сколько бы чатов его ни получали.

Воркер скачивает звук через `yt-dlp`, перекодирует в MP3 через `ffmpeg` и
отправляет через Telegram Bot API со ссылкой «Original upload» в подписи.
Неудачная попытка освобождает ключ и падает с исключением, и SQS повторяет её.
После трёх неудачных получений сообщение не пропадает, а уходит в `VideoDLQ`.

### Зачем тут каждая деталь

- **Вебхук только ставит в очередь.** Lambda замораживает экземпляр сразу
  после ответа, поэтому продолжить работу в фоновом потоке после `202` нельзя.
  Всё скачивание идёт в отдельном вызове воркера.
- **Вебхук — zip на стандартной библиотеке**, а воркер — контейнер. Вебхук
  должен быстро отвечать на проверку хаба, и его холодный старт занимает доли
  секунды. Воркеру нужны `ffmpeg` и `deno`, поэтому он собран в образ ~1 ГБ с
  холодным стартом ~10 с — но его никто не ждёт.
- **Параллельность воркера ограничена на источнике событий SQS**
  (`MaximumConcurrency`), а не зарезервированной параллельностью. У новых
  аккаунтов AWS лимит параллельности Lambda — 10, и зарезервировать из него
  часть нельзя.
- **`/tmp` в Lambda — настоящий временный диск** (здесь 4 ГБ). Он не отнимает
  память функции, поэтому длинные миксы помещаются без увеличения инстанса.
- **Обложка идёт двумя путями.** Bot API принимает `thumbnail` не больше
  320×320 и 200 КБ. Поэтому воркер обрезает лучшую превьюшку YouTube
  (1280×720) до центрального квадрата — там, между чёрными полосами, и стоит
  обложка релиза. Полную обложку 720×720 он вшивает в ID3-теги MP3 вместе с
  исполнителем и названием, а копию 320×320 отправляет как `thumbnail`. Ещё
  трек несёт длительность из метаданных YouTube: без неё клиенты Telegram
  могут показывать `0:00` для VBR MP3, пока его не включишь.

## Деплой

### Что понадобится

- AWS CLI с ключами — лучше IAM-пользователя, а не root-аккаунта
- [AWS SAM CLI](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/install-sam-cli.html)
- Запущенный Docker: `sam build` собирает образ воркера локально
- Python 3.11+; PyYAML нужен только для `tools/channels.py import` (`pip install pyyaml`)
- Бот Telegram и группа Telegram для управления им, куда бот добавлен
  участником

### 1. Секреты

Оба секрета лежат в SSM Parameter Store, шаблон знает только их имена.
Стандартные параметры бесплатны.

```bash
aws ssm put-parameter --name /autouploadbot/bot-token \
  --type SecureString --value 'TELEGRAM_BOT_TOKEN'

aws ssm put-parameter --name /autouploadbot/hub-secret \
  --type SecureString --value "$(openssl rand -hex 32)"
```

`hub-secret` общий с хабом WebSub: хаб подписывает им каждое уведомление.
Function URL вебхука публичный поневоле — хаб не умеет аутентифицироваться в
AWS, — поэтому всё без правильного `X-Hub-Signature` вебхук отклоняет с `403`.

Третий секрет, `/autouploadbot/telegram-secret`, так же защищает вебхук
бота-пульта. Его создаёт `tools/telegram_webhook.py` после первого деплоя.

### 2. Параметры

```bash
cp samconfig.toml.example samconfig.toml
```

| Параметр | Что значит |
| --- | --- |
| `AdminChatId` | ID служебной группы: туда приходят алерты, и любой её участник может управлять ботом. Добавьте бота в группу, напишите туда что-нибудь и возьмите `chat.id` из `getUpdates` — это отрицательное число. |
| `AdminUtcOffset` | Сдвиг от UTC в часах для времени, которое показывает бот-пульт, например `3` или `5.5`. По умолчанию `0`. |
| `LeaseSeconds` | Срок подписки WebSub, по умолчанию и максимум — `432000` (5 дней). |
| `WorkerConcurrency` | Сколько треков качается параллельно, по умолчанию `5`, минимум `2`. |
| `BotTokenParam`, `HubSecretParam`, `TelegramSecretParam` | Имена параметров SSM, по умолчанию — как выше. |

### 3. Деплой

```bash
sam build && sam deploy
```

При первом деплое SAM предупредит, что у `WebhookFunction` и
`AdminBotFunction` нет аутентификации. Отвечайте `y` — так и задумано: обе
функции сами проверяют секрет.

### 4. Подключение бота-пульта

```bash
python3 tools/telegram_webhook.py          # секрет, вебхук, /menu и /status
python3 tools/telegram_webhook.py --info   # что сейчас знает Telegram
```

Запустите один раз; повторно — только если изменится output `AdminBotUrl`.
После этого бот получает апдейты через вебхук, и `getUpdates` для него
перестаёт работать.

### 5. Каналы

Отправьте `/menu` в служебную группу и нажмите **➕ Добавить канал** — см.
[Служебный чат](#служебный-чат). Чтобы загрузить сразу много каналов, опишите
их в файле:

```bash
cp channels.yaml.example channels.yaml
python3 tools/channels.py import           # проверить и записать в ChannelsTable
python3 tools/channels.py list             # что сейчас в таблице
python3 tools/channels.py export           # сохранить таблицу в channels.yaml
```

```yaml
- name: My channel                   # необязательно, для себя
  youtube: UCxxxxxxxxxxxxxxxxxxxxxx
  telegram: -1001234567890           # один чат…

- name: Another channel
  youtube: UCyyyyyyyyyyyyyyyyyyyyyy
  telegram:                          # …или несколько
    - -1001234567890
    - "@public_mirror"
```

`import` проверяет, что у каждого ID YouTube есть фид (и что его автор
совпадает с `name`) и что бот — админ с правом публикации в каждом чате, а
затем добавляет или обновляет записи. Каналы, которых нет в файле, остаются
как были. `channels.yaml` в `.gitignore`: ID чатов — личные данные. ID каналов
и супергрупп начинаются с `-100`; без минуса Telegram отвечает
`chat not found`. Публичный канал можно указать как `"@username"`.

### 6. Первый запуск

```bash
STACK=autouploadbot   # ваш stack_name
out() { aws cloudformation describe-stacks --stack-name "$STACK" \
  --query "Stacks[0].Outputs[?OutputKey=='$1'].OutputValue" --output text; }

# подписаться сразу, не дожидаясь ежечасного запуска
aws lambda invoke --function-name "$(out ResubscribeFunctionName)" /dev/stdout
```

Первый запуск `PollFunction` для канала (в течение 15 минут) ничего не
публикует: он отмечает 15 видео, уже лежащих в фиде, как просмотренные. Иначе
в чат вывалился бы весь бэк-каталог. С каналом, добавленным позже, происходит
то же самое.

## Служебный чат

`AdminBotFunction` превращает служебную группу в пульт управления. Пользоваться
им может любой участник группы; апдейты из других чатов и из лички бот
игнорирует. Telegram подписывает каждый апдейт секретом `telegram-secret`, а
всё остальное функция отклоняет с `403`.

| Экран | Что делает |
| --- | --- |
| 📊 Статус | глубина очереди и DLQ, результат пробы cookies, сработавшие алярмы, сколько треков ушло в каждый чат за сутки |
| 🔔 Подписки | состояние и срок подписки WebSub каждого канала по данным хаба |
| 📺 Каналы | все каналы с их зеркалами: добавить или убрать зеркало, выложить последние 3 видео, удалить канал |
| ➕ Добавить канал | диалог: ссылка на YouTube или `@handle` → чат → подтверждение, по желанию — сразу с последними 3 видео |

Чат выбирают так: пересылают любой пост из него, присылают его `@username` или
жмут кнопку. Когда бота делают админом в канале, он это запоминает, сразу
предлагает **➕ Привязать** и показывает канал на шаге выбора чата. Перед
сохранением бот проверяет, что может туда писать.

Новый канал сразу подписывается на хабе. При удалении канал отписывается, а
отметки о просмотренных видео стираются, чтобы при повторном добавлении в чат
не вывалился бэк-каталог.

Диалог идёт в одном сообщении, которое бот редактирует по шагам. Состояние
хранится в `BotStateTable` час, потому что Lambda ничего не помнит между
апдейтами. `/menu` и `/status` работают в любой момент, а под каждым алертом
тоже есть кнопка **📊 Статус**.

Новый канал или зеркало начинается пустым. Кнопка **⏪ Залить последние 3** в
карточке канала ставит последние видео в очередь с интервалом в пару минут,
от старых к новым, и пропускает то, что в чате уже есть. Для нескольких
каналов сразу есть скрипт:

```bash
python3 tools/backfill.py --latest 3 [--channel UC…] [--dry-run]
```

Он ставит видео в очередь волнами — сначала самые старые, следующие после того,
как очередь опустеет, — поэтому каждый чат получает их в порядке YouTube.

## Названия

Воркеру нужны исполнитель и название трека. Название видео делится по первому
найденному из ` — `, ` – `, ` - ` (длинное тире, короткое тире, дефис — каждый
с пробелами вокруг), именно в таком порядке. Поэтому в
`Artist — Track - Extended Mix` дефис остаётся внутри названия трека.
Каталожный номер в конце вида `[CATALOG123]` убирается. Видео без этих
разделителей пропускаются с записью в лог.

## YouTube с IP дата-центра

Без подготовки YouTube отвечает на запросы из AWS
`Sign in to confirm you're not a bot`. Чтобы пройти проверку, нужны две вещи,
и обе обязательны:

1. **Среда JavaScript и решатель подписей.** В образе есть `deno`, а
   зависимость — `yt-dlp[default]`, которая подтягивает `yt-dlp-ejs`. Без
   решателя `deno` бесполезен: подписи не решаются, и yt-dlp падает с
   `Requested format is not available`.
2. **Cookies залогиненного аккаунта** в `CookiesBucket`. Воркер копирует их в
   `/tmp` при каждом холодном старте.

Берите отдельный аккаунт, не основной: регулярные скачивания с IP дата-центра
с его cookies могут привести к блокировке.

Выгружайте cookies из **приватного окна (инкогнито)**, а не из обычной сессии
браузера. Браузер постоянно обновляет cookies активной сессии, и выгруженная
копия такой сессии умирает в течение часа. Войдите в аккаунт, откройте любое
видео, затем DevTools → Application → Cookies → `https://www.youtube.com`,
выделите все строки и скопируйте. Закройте окно, не выходя из аккаунта —
выход обнуляет сессию, — и больше эту сессию не используйте.

Затем **наберите руками** (не копируйте — иначе затрёте cookies в буфере
обмена):

```bash
tools/upload_cookies.sh
```

Скрипт конвертирует буфер обмена через `tools/curl_to_cookies.py`, загружает
результат в `CookiesBucket` стека из `samconfig.toml` и удаляет локальную
копию. Конвертер понимает строки из Application → Cookies, «Copy as cURL» из
вкладки Network и голое значение заголовка `Cookie`. Значения cookies он
никогда не печатает и отказывается от всего, где нет признаков залогиненной
сессии. Если в буфере оказалось что-то другое, загрузка остановится, а не
заменит рабочие cookies мусором.

Когда cookies протухают, скачивания падают с
`Sign in to confirm you're not a bot`, и видео копятся в `VideoDLQ`. Загрузите
свежие cookies и верните упавшие видео в очередь:

```bash
aws sqs start-message-move-task --source-arn \
  "$(aws sqs get-queue-attributes --queue-url "$(out DeadLetterQueueUrl)" \
     --attribute-names QueueArn --query Attributes.QueueArn --output text)"
```

Дедупликация пропустит всё, что уже дошло до чата. Сообщения хранятся в DLQ
14 дней — считая с момента, когда видео впервые попало в очередь.

## Подписка WebSub

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/websub-handshake-dark.png">
  <img alt="Последовательность: EventBridge запускает ResubscribeFunction, она проверяет состояние подписки и отправляет запрос на подписку; хаб проверяет callback через challenge, затем присылает подписанные уведомления" src="docs/images/websub-handshake-light.png">
</picture>

Подписка начинает работать только после проверки хабом: он отправляет на
callback `GET` со случайным `hub.challenge`, и callback должен вернуть его
обратно. До этого хаб держит запрос в состоянии `unverified` и ничего не
присылает. Проверка нужна, чтобы никто не мог подписать чужой URL на поток
уведомлений.

`ResubscribeFunction` работает по двум расписаниям:

| Расписание | Payload | Что делает |
| --- | --- | --- |
| `Retry`, каждый час | `{"force": false}` | повторно отправляет подписки, которые ещё не `verified` |
| `Renew`, раз в сутки | `{"force": true}` | продлевает все подписки независимо от состояния |

Каналы обрабатываются параллельно: хаб может держать каждый запрос ~20 с.
`5xx` или таймаут хаба пишется в лог как «degraded» и не роняет запуск; `4xx`
значит, что неверны наши параметры, — и роняет.

Проверить состояние:

```bash
sam logs --stack-name "$STACK" -n ResubscribeFunction | grep 'state='
```

> [!NOTE]
> Хаб может лежать днями. С 19 по 21 сентября 2026
> `pubsubhubbub.appspot.com` отвечал на каждый запрос подписки
> `503 Transient error` через ~20 с и не присылал проверку, так что все
> подписки оставались `unverified`. Ничего не потерялось: все видео доставил
> опрос RSS, а когда хаб ожил, ежечасное расписание подтвердило подписки без
> вмешательства. Именно поэтому `5xx` от хаба пишется в лог как «degraded».

В качестве topic используйте настоящий фид канала,
`https://www.youtube.com/feeds/videos.xml?channel_id=…`. Похожий
`/xml/feeds/videos.xml` — статическая заглушка на 463 байта, которая
игнорирует `channel_id`. Функция собирает URL сама, так что это важно только
при ручной подписке.

## Проверка без хаба

```bash
python3 tools/send_test_event.py \
  --video 'https://www.youtube.com/watch?v=VIDEO_ID' \
  --title 'Artist — Track' \
  --channel UC…            # маршрутизировать как видео этого канала
```

Скрипт подписывает поддельное уведомление Atom тем же `hub-secret` и
отправляет его на вебхук, так что всё после хаба работает по-настоящему:
проверка подписи, очередь, воркер, YouTube, Telegram. Трек действительно
публикуется. Повторный запуск для того же видео ничего не сделает —
дедупликация его пропустит. `--channel` по умолчанию — первый канал из
`ChannelsTable`, имя стека — `stack_name` из `samconfig.toml`.

## Эксплуатация

```bash
sam logs --stack-name "$STACK" --tail                   # все функции
sam logs --stack-name "$STACK" -n WorkerFunction --tail

aws sqs receive-message --queue-url "$(out DeadLetterQueueUrl)"   # упавшие видео
```

В консоли стек виден в CloudFormation → Stacks, в регионе из
`samconfig.toml`. Считайте его доступным только для чтения: `sam deploy`
затирает ручные изменения.

Каждый деплой воркера добавляет образ в ECR. Храните только два последних:

```bash
aws ecr put-lifecycle-policy --repository-name <repo> --lifecycle-policy-text \
  '{"rules":[{"rulePriority":1,"description":"keep last 2","selection":{"tagStatus":"any","countType":"imageCountMoreThan","countNumber":2},"action":{"type":"expire"}}]}'
```

## Алерты

Три алярма CloudWatch пишут в служебный чат — и когда что-то сломалось, и
когда починилось:

| Алярм | Когда срабатывает | Обычно значит |
| --- | --- | --- |
| `DeadLetterAlarm` | сообщение попало в `VideoDLQ` | видео упало три раза — протухли cookies или файл больше 50 МБ |
| `QueueStuckAlarm` | сообщение ждёт в `VideoQueue` больше часа | воркер не запускается или падает до обработки |
| `CookieProbeAlarm` | ежечасная проба cookies не прошла | cookies протухли — загрузите свежие, пока треки не начали падать |

Проба cookies раз в час запускает `WorkerFunction` с `{"probe": true}`. Она
запрашивает у YouTube метаданные свежего видео ровно так, как это делает
настоящее скачивание — с cookies и решением подписей, — но ничего не качает,
а результат пишет в метрику `autouploadbot/CookieProbe`. Исключений проба
никогда не бросает: иначе EventBridge Scheduler повторял бы упавший запуск до
185 раз.

Алярм → топик SNS → `AlertFunction` → Telegram. Проверить цепочку, ничего не
ломая:

```bash
aws cloudwatch set-alarm-state --state-value ALARM --state-reason test \
  --alarm-name "$(aws cloudwatch describe-alarms --alarm-name-prefix "$STACK-CookieProbe" \
     --query 'MetricAlarms[0].AlarmName' --output text)"
```

При следующей оценке алярм вернётся в `OK` и пришлёт сообщение о
восстановлении.

## Стоимость

Из расчёта 200–400 треков в месяц — несколько каналов, выкладывающих по
одному-два видео в день:

| Сервис | Потребление | Стоимость |
| --- | --- | --- |
| Lambda | ~20–30 тыс. ГБ·с, несколько тысяч вызовов; бесплатный лимит — 400 тыс. ГБ·с | $0 |
| ECR | образы воркера, ~350 МБ каждый, плюс один за каждый деплой | ~$0,20, ~$0,07 с правилом хранения выше |
| DynamoDB on-demand | опрос читает таблицу просмотренных, пишет только новые видео | ~$0,02 |
| SQS, EventBridge Scheduler, S3, SSM, исходящий трафик | глубоко в бесплатных лимитах | $0 |

Число чатов почти не влияет: видео скачивается один раз, а каждый лишний чат
стоит секунду отправки и ~10 МБ трафика. Трек обрабатывается 15–50 с при
2 ГБ памяти, так что бесплатного лимита Lambda хватает примерно на 8–10 тысяч
треков в месяц. Пик памяти — ~600 МБ, поэтому `MemorySize` можно снизить до
1024 ценой более медленного `ffmpeg`: CPU в Lambda растёт вместе с памятью.

## Известные ограничения

- Telegram Bot API не принимает файлы больше 50 МБ, поэтому длинные миксы
  падают на отправке — уже после скачивания и конвертации.
- Один вызов Lambda ограничен 15 минутами на трек.
- Удалённое видео приходит как `<at:deleted-entry>`; вебхук пишет в лог
  `Unparseable notification body` и отвечает `200`, чтобы хаб не повторял.
- Cookies YouTube протухают, и время от времени их нужно выгружать заново.

## Схемы

Картинки выше — скриншоты интерактивных схем, сделанных в
[archify](https://github.com/tt-a1i/archify). Интерактивные версии — с
масштабированием, поиском, подсветкой связей, светлой и тёмной темой,
экспортом — лежат в `docs/diagrams/*.html`: скачайте файл и откройте в
браузере. Рядом лежат исходники `.json`:

```bash
ARCHIFY=<path-to-archify>/bin/archify.mjs
node $ARCHIFY deliver architecture docs/diagrams/architecture.json docs/diagrams/architecture.html --quality showcase
node $ARCHIFY deliver sequence docs/diagrams/video-pipeline.json docs/diagrams/video-pipeline.html --quality showcase
node $ARCHIFY deliver sequence docs/diagrams/websub-handshake.json docs/diagrams/websub-handshake.html --quality showcase
```

Затем замените PNG в `docs/images/` скриншотом или экспортом каждой схемы — в
светлой и тёмной теме.
